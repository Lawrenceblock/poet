## 二、实际审阅入口（唯一推荐入口）

### 2.1 入口是什么

**【事实】** 审阅入口是**独立启动的本地审阅服务**，不是公开诗歌站、也不是 Vercel 预览站：

- 服务程序：`tools/review/serve_review.py`（Python 标准库，无第三方依赖）。
- 它同时提供：静态阅读页 + `/review/api/*` 接口。
- 服务把“静态预览目录”与“记录目录”分离开：阅读页在 `hugo/public/review/`（构建产物），
  记录在 `docs/author-review/review-records/`（私人，已 gitignore）。

### 2.2 完整访问网址

```
https://<预览主机>/review/?token=<令牌>
```

- `<预览主机>`：由助手启动服务时所在的主机（例如 `…prod-runtime.all-hands.dev`，端口 12000）。
- `<令牌>`：助手设置的 `REVIEW_ACCESS_TOKEN`。**本报告不记录任何真实令牌。**
- 首次带 `?token=` 打开后，服务会**立刻把令牌从网址里去掉**（返回 303 跳转），
  并在浏览器写入 Cookie，后续页面不再需要令牌。

### 2.3 入口是否已经可以使用

**【事实】** 系统**功能可用且已实测**，但**目前未处于运行状态**：

- 实测（隔离环境 + 合成数据）通过：未授权 401、带令牌 200、保存、回读、进度、导出、POST 转发。
- 当前工作主机的 `/review/` 返回 **502**（服务未启动）。
- Vercel 预览站 **不提供** `/review/`（见 2.4）。

### 2.4 Vercel 预览站的情况（重要）

**【事实】** 对 PR #21 的 Vercel 预览地址实测：

| 路径 | 结果 |
| --- | --- |
| `/` | 200（公开诗歌首页正常） |
| `/archive/`、`/search/` | 200 |
| `/review/`、`/review/poem/C0001.html`、`/review/api/health` | **404** |
| 首页是否含 `/review/` 链接 | **没有** |

原因：`hugo/hugo.toml` 中 `enableReview = false`（**默认关闭**），只有 `tools/preview/build_preview.py`
在本地构建时用 `HUGO_PARAMS_ENABLEREVIEW=true` 临时开启。**Vercel 用 `hugo/vercel.json` 的
`hugo --gc --minify` 构建，不设该变量，因此 Vercel 上根本没有 `/review/`。**

> **【事实】** 这是**有意的安全设计**：正式站点绝不发布未经确认的作品全文与审阅接口。
> 但它也意味着：**作者审阅必须在“本地审阅服务”上进行，而不是在 Vercel 预览站上。**

### 2.5 多入口时推荐哪一个

**【建议】** 只推荐**一个**入口：**总目录 `/review/`**（经审阅服务 + 令牌）。
它是唯一的“一站式”入口：有进度、有筛选、能进入每一条、能导出。其它路径（批次页、单条页）
都从它进入，不需要单独记。

## 三、作者如何使用（直接回答五个问题）

**第一：我应该打开哪个网址？**
`https://<预览主机>/review/?token=<令牌>`（由助手提供主机与令牌）。

**第二：打开后第一步应该做什么？**
先看顶部**审阅进度**（应显示“共 137 篇…未审阅 137 篇”），确认服务正常；再点某一行的 **“阅读/审阅”**。

**第三：如何审阅第一条记录并保存？**
读完整原文 → 选 **①审阅结论**（保留/暂缓/排除/待审阅）→ 选 **②作品性质**（一首/多首/非诗/尚不确定/未填写）→
可选写 **③作者意见** → 点底部 **“保存审阅”**。

**第四：如何确认保存成功并继续下一条？**
看到绿色 **“保存成功”** 且出现 **“上次保存：…（第 N 版）”** 即成功 → 点 **“← 审阅总目录”** → 点下一条。

**第五：现在能正式开始审阅吗？**
**还不能。** 阻塞点是一个**数据前置问题**（见第五节）：真实记录目录的权威流水账
`journal.jsonl` 缺失。在此状态下：备份/恢复会**拒绝执行**（fail-closed），且**任何一次保存都会把
快照/导出按“新流水账”重建**，只反映保存过的记录。**请作者先看第五节并作出决定。**

### 5.3 需要作者先决定的阻塞问题

**【事实】** 真实记录目录处于异常状态：`journal.jsonl` **缺失**，而派生文件仍在
（`snapshot.json` 计数 0；`decisions.jsonl` 137 行；导出 137 行；全部为 `pending`）。
据前几轮报告，此目录曾经历沙盒恢复，`journal` 未能找回。

**【事实·实测影响】**

1. **备份/恢复会拒绝**：`backup_review_data.py` 对“journal 缺失但派生文件仍在”的目录
   一律**拒绝**（fail-closed，防静默丢数据）。**因此在解决前，无法做正式备份。**
2. **保存会重建派生文件**：`store.save()` 成功后调用 `rebuild()`，由 `journal.jsonl`（当前为空）
   重放生成 `snapshot/decisions/导出`。实测：在“旧 snapshot 有 137 条 pending、journal 为空”的
   目录里保存 1 条 → **snapshot 从 137 条变成 1 条**。
   > **【推断】** 现有 137 行 `decisions.jsonl` 等派生文件**很可能是从别处恢复出来的“副本”**，
   > 而非本机权威流水账；因此“保存会把 137 条派生行重建成只含新记录”**不一定会丢真实的作者决定**
   > （它们本就以 `pending` 占位、非真实决定）。**但这一点未经证实，必须由作者/助手确认后再操作。**

**【建议】** 作者正式开审**前**，请助手按以下之一处理（二选一，**均不改动诗歌正文**）：

- **方案 A（推荐，最安全）**：把现有派生文件**另存归档**（保留证据），然后在记录目录中
  **建立一份全新的空 journal**（或让助手用受控的 `rebuild` 流程建立合法空基线），
  使“137 篇待审阅”成为干净的起点，再开始审阅。
- **方案 B**：请助手先查私有远端/备份，确认是否存在**完整且校验通过**的 journal 副本；
  若有，`verify` 后 `restore`，再开始审阅。

> 在作者明确选择之前，**不要**在真实目录里做任何保存或备份/恢复操作。

6. 之后再按批次正式审阅；**每批结束导出 + 备份**。
