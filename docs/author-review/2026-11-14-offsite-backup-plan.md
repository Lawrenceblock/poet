## 0. 为什么必须异地

**【事实】** 本沙盒中记录在 `/workspace`（ext4，设备号 66309），默认备份目录在容器
overlay（设备号 240）——**不同文件系统，但同一容器**。整个沙盒回收时两者一起丢失。
**【事实】** 上一批 19 条作者决定正是这样丢失的。
**【推断】** 唯一能真正抵御沙盒回收的，是**把备份送出这台机器**。

## 1. 两种可行方案比较

| 维度 | A. 独立私有 Git 仓库 | B. 独立对象存储 |
| --- | --- | --- |
| 可否用现有账户/免费额度 | **可以**：作者已有的 GitHub/GitLab 私有仓库；免费额度足够（文本备份极小，单份 < 100 KB） | **视情况**：多数云厂商对象存储有免费额度或极低费用；**需作者已有账户**，本轮不新建、不购买 |
| 抵御整沙盒回收 | **是**（数据在平台侧） | **是** |
| 历史版本 | **是**（Git 提交历史，天然版本化） | **部分**：需开启版本控制（versioning）才有；否则覆盖即丢失 |
| 完整性校验 | **是**：仓库内已有 `SHA256SUMS.txt` + `manifest.json`，且 Git 自身对每个对象做哈希 | **是**：`SHA256SUMS.txt` + 对象存储 ETag/校验和 |
| 能否恢复 | **是**：`git clone` 后 `backup_review_data.py verify` → `restore` | **是**：下载后同样 `verify` → `restore` |
| 是否让公开诗歌仓库接触私人意见 | **否**（备份在**独立私有仓库**，与公开 `poet` 仓库完全分离） | **否**（在对象存储中，与 Git 无关） |
| 维护复杂度 | **低**：一个 `git push`；无需额外凭据体系 | **中**：需管理 bucket、访问密钥、版本控制策略 |
| 加密 | **建议**：Git 仓库虽私有，仍建议对备份内容做**本地加密**后再提交（见第 3 节） | **建议**：上传前本地加密（对象存储密钥一旦泄漏风险更高） |
| 成本 | **零**（用现有私有仓库） | **零～极低**（免费额度内） |

### 结论

**【建议】优先 A（独立私有 Git 仓库）**，理由：最简单、零新增成本、天然版本化、
与公开仓库彻底分离、校验方式与现有 `SHA256SUMS.txt` 完全契合、长期可维护。
**若作者不希望再多维护一个仓库**，则用 B，但**必须开启版本控制**。

**两者都必须：**
1. **独立于公开仓库** `Lawrenceblock/poet`——绝不把私人意见放进公开仓库。
2. **上传前本地加密**（见第 3 节），做到“即使远端被误设为公开也不泄漏”。
3. 上传的是**加密后的备份文件**，不是明文 `journal.jsonl`。

## 2. 推荐实施步骤（待作者确认后再执行）

**【建议】以方案 A 为例：**

1. 作者提供一个**私有**仓库（例如 `Lawrenceblock/poet-review-backup`，**私有**）。
2. 本地生成备份：`python3 tools/review/backup_review_data.py backup`。
3. 对备份目录**加密打包**（见第 3 节），产出一个 `.tar.gz.age` 或 `.tar.gz.gpg`。
4. `git push` 到**私有**仓库（或对象存储上传）。
5. 恢复演练：在空目录 `git clone` → 解密 → `verify` → `restore`，确认可用。
6. 定期（每次审阅后）重复 2–4；Git 历史自动保留每次版本。

**【事实】** 环境已具备 `openssl 3.5.7`、`gpg`、`tar`，可离线加密，无需联网工具。

---

## 3. 加密建议（上传前）

**【建议】** 用对称加密（口令由作者持有，不写入仓库、不写入本对话）：

```bash
# 打包 + 加密（示例：openssl AES-256）
tar czf - <备份目录> | openssl enc -aes-256-cbc -pbkdf2 -salt -out backup.tar.gz.enc
# 解密恢复
openssl enc -d -aes-256-cbc -pbkdf2 -in backup.tar.gz.enc | tar xzf -
```

或用 `age`/`gpg`。**密钥/口令绝不能提交到任何仓库**，也不应出现在本对话或报告中。
